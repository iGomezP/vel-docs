## PostgreSQL Schema Design

The initial PostgreSQL relational model for VEL Workbench was designed before implementing the persistence layer.

The schema was derived from the existing VEL Workbench domain model rather than directly creating database tables.

Initial domain concepts include:

- Projects.
- Work Items.
- Work Item States.
- Sprints.
- Labels.
- Comments.
- Activity Events.
- Evidence Links.

### Identifier Strategy

UUIDv7 was selected for domain entity primary keys.

Identifiers will be generated by the .NET application using:

```text
Guid.CreateVersion7()
```

Human-readable identifiers such as:

```text
VW-001
VW-002
```

remain separate from database primary keys.

### Work Item Number Allocation

Work item numbers must be sequential within a project.

The design intentionally avoids:

```text
MAX(number) + 1
```

because concurrent requests could allocate the same number.

Each project instead maintains an atomic:

```text
next_work_item_number
```

counter.

PostgreSQL row locking and:

```text
UNIQUE (project_id, number)
```

will provide consistency under concurrent work item creation.

### Activity History

Activity events were defined as append-only engineering history.

The design includes:

```text
actor_type
actor_reference
```

without introducing a User entity during the single-user MVP.

Activity history is not intended to implement Event Sourcing.

Current application state remains stored in the relational domain tables.

### Referential Integrity

Delete behavior was explicitly defined.

Core domain relationships favor:

```text
ON DELETE RESTRICT
```

to preserve engineering history.

Optional Sprint membership uses:

```text
ON DELETE SET NULL
```

Associative Work Item / Label records may use:

```text
ON DELETE CASCADE
```

because those records do not represent independent engineering history.

### Data-Intensive Design

PostgreSQL was established as the authoritative source of truth for transactional VEL Workbench state.

Redis and RabbitMQ will not be introduced merely because they are available in the VEL platform.

They will be introduced only when real access patterns or asynchronous workflows justify them.

The schema is designed around known MVP query patterns rather than speculative functionality.

## Backend Persistence Foundation

EF Core persistence was introduced into the .NET 10 backend.

### Technology

The persistence stack currently uses:

```text
.NET 10
EF Core 10.0.11
Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3
PostgreSQL 17
```

### Configuration

Database configuration was implemented using the .NET Options pattern.

The application consumes configuration through:

```text
IConfiguration
Options
Environment Variables
```

rather than coupling application code directly to a particular configuration source.

This leaves the architecture open for a future centralized VEL configuration platform.

Sensitive credentials are not committed to Git.

Environment variables currently provide local secrets.

Future platform direction may separate:

```text
Central Configuration
```

from:

```text
Secret Management
```

with a dedicated secret store such as Vault being evaluated later.

## Architecture Direction

VEL Workbench continues to follow a modular monolith architecture.

The backend will evolve through small vertical slices rather than implementing every database entity and repository at once.

The frontend follows a feature-first Screaming Architecture.

The intended direction is:

```text
Next.js
    ↓
VEL Workbench API
    ↓
Application Use Case
    ↓
Domain
    ↓
EF Core
    ↓
PostgreSQL
```

Infrastructure capabilities such as caching, messaging, centralized configuration, secrets management, and observability will be introduced incrementally when concrete requirements justify them.

---

## Decisions and Lessons

Several engineering principles were reinforced during this session:

- Design the data model before generating the physical schema.
- Do not introduce infrastructure without a concrete requirement.
- Treat PostgreSQL as the authoritative transactional source of truth.
- Keep secrets outside version control.
- Separate configuration consumers from configuration providers.
- Design concurrency explicitly instead of assuming single-user execution.
- Preserve engineering history by default.
- Review generated migrations before applying them.
- Implement small vertical slices rather than building all layers horizontally.
- Keep architecture evolvable without prematurely implementing future requirements.
