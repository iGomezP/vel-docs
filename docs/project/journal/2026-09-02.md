# Engineering Journal — 2026-09-02

## Incident: VS Code Remote-SSH failure after Fedora upgrade

**Status:** Resolved  
**Host:** `vakzor-lab`  
**Client:** Windows / VS Code 1.136.0  
**Remote:** Fedora 44  
**Remote-SSH:** 0.128.0  
**SELinux:** Enforcing

### Summary

After running:

    sudo dnf upgrade -y

VS Code Remote-SSH stopped connecting successfully to `fedora-lab`.

Regular SSH authentication continued to work, but VS Code failed when attempting
to establish port forwarding to the VS Code Server running on the Fedora host.

### Symptoms

SSH itself worked:

    ssh fedora-lab

VS Code Server was also able to start successfully and listen on localhost.

However, Remote-SSH repeatedly failed with:

    channel 2: open failed: connect failed: open failed

Both dynamic forwarding and direct local forwarding were investigated.

The effective SSH server configuration confirmed that forwarding was enabled:

    allowtcpforwarding yes
    disableforwarding no
    permitopen any
    permitlisten any

This ruled out `sshd_config` as the cause.

### Root Cause

SELinux was blocking `sshd-session` from connecting to the ephemeral TCP port
used by the VS Code Server.

The denial was confirmed using:

    sudo ausearch -m AVC,USER_AVC -ts recent

Relevant AVC:

    avc: denied { name_connect }
    comm="sshd-session"
    scontext=system_u:system_r:sshd_session_t:s0-s0:c0.c1023
    tcontext=system_u:object_r:ephemeral_port_t:s0
    tclass=tcp_socket
    permissive=0

Temporarily switching SELinux to permissive mode:

    sudo setenforce 0

allowed VS Code Remote-SSH to connect, confirming SELinux as the blocking layer.

SELinux was NOT left disabled.

### Resolution

A minimal local SELinux policy module was generated for the observed
`sshd-session` denial.

Required tooling:

    sudo dnf install -y policycoreutils-python-utils

Policy generation:

    sudo ausearch -c 'sshd-session' -m AVC -ts recent | audit2allow -M vscode-ssh

The generated policy was reviewed before installation.

The required permission was:

    allow sshd_session_t ephemeral_port_t:tcp_socket name_connect;

The module was installed with:

    sudo semodule -i vscode-ssh.pp

SELinux was kept in enforcing mode:

    sudo setenforce 1

### VS Code workaround

The following Remote-SSH settings are currently retained:

    "remote.SSH.useExecServer": false,
    "remote.SSH.enableDynamicForwarding": false

With these settings and the local SELinux policy installed, Remote-SSH connects
successfully while SELinux remains enforcing.

### Validation

SELinux state:

    getenforce

Expected:

    Enforcing

Installed policy:

    sudo semodule -l | grep vscode

Result:

    vscode-ssh

AVC verification after successful Remote-SSH connection:

    sudo ausearch -m AVC,USER_AVC -ts 23:23:00

Result:

    <no matches>

VS Code Remote-SSH also confirmed successful creation and reuse of the exec
server:

    Exec server for ssh-remote+fedora-lab created and cached
    Verified and reusing cached exec server for ssh-remote+fedora-lab

### Lessons Learned

- Successful SSH authentication does not guarantee SSH port forwarding is
  permitted by all security layers.
- `sshd_config` was correctly configured; SELinux was the actual blocking layer.
- AVC logs should be checked before weakening or disabling SELinux.
- `setenforce 0` is useful as a diagnostic step, not as a permanent fix.
- Local SELinux exceptions should be minimal, reviewed, documented, and
  reversible.
- Infrastructure upgrades can introduce security-policy behavior changes even
  when the SSH daemon configuration itself has not changed.

### Rollback

The local SELinux policy can be removed with:

    sudo semodule -r vscode-ssh

Verify:

    sudo semodule -l | grep vscode
