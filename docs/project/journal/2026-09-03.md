### Query Use Case

Added:

```text
Application/Projects/GetProjectById/
├── GetProjectByIdQuery.cs
└── GetProjectByIdHandler.cs
```

`GetProjectByIdQuery` represents the read request while `GetProjectByIdHandler` delegates Project retrieval to the repository.

The handler returns `Project?` and deliberately remains unaware of HTTP semantics.

A missing Project is represented as `null` at the application boundary and translated to HTTP `404 Not Found` by the API layer.

### Persistence

`ProjectRepository` now implements:

```csharp
Task<Project?> GetByIdAsync(
    Guid id,
    CancellationToken cancellationToken = default);
```

Retrieval is performed through EF Core using `WorkbenchDbContext`.

### HTTP API

Added:

```text
GET /projects/{id:guid}
```

Observed behavior:

```text
Existing Project ID     -> 200 OK
Unknown valid GUID      -> 404 Not Found
Invalid GUID such as abc -> 404 Not Found
```

The `guid` route constraint allows ASP.NET Core routing to reject invalid route identifiers before the request reaches the application handler.

## Engineering Decisions

### Let real use cases drive abstractions

`IProjectRepository` was initially scoped under `CreateProject` because creation was its only consumer.

Once Project retrieval became a real use case, the interface was promoted to the shared Projects application scope.

This avoids speculative architecture while still allowing the design to evolve when concrete requirements demonstrate a shared responsibility.

### Keep HTTP semantics at the API boundary

`GetProjectByIdHandler` returns `Project?`.

It does not return HTTP-specific results or know about status codes.

The API layer translates:

```text
Project -> 200 OK
null    -> 404 Not Found
```

### Avoid unnecessary async state machines

`GetProjectByIdHandler` directly returns the repository `Task<Project?>` because it performs no intermediate asynchronous processing.

`CreateProjectHandler`, in contrast, uses `async/await` because it must inspect asynchronous results, make decisions, and perform multiple asynchronous operations.

## Lessons Reinforced

- Refactor abstractions when real duplication of responsibility appears.
- Do not introduce CQRS infrastructure simply because commands and queries now exist.
- Keep application behavior independent from HTTP semantics.
- Route constraints are useful infrastructure-level validation.
- Fakes must evolve when their implemented contracts evolve.
- A resource URI returned by a creation endpoint should eventually represent a real retrievable resource.
- Automated tests should remain green during structural refactoring.
- Operational troubleshooting should produce reusable runbooks rather than remain only in terminal history.
