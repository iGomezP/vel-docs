### VW-012 — Implement concurrency-safe Work Item numbering

Introduced a dedicated Application abstraction:

```text
IWorkItemNumberAllocator
```

The allocator is intentionally separate from `IProjectRepository` because Work Item number allocation is a concurrency-sensitive capability used by Work Item creation rather than normal Project CRUD.

Implemented PostgreSQL allocation using an atomic statement:

```sql
UPDATE projects
SET next_work_item_number = next_work_item_number + 1
WHERE id = @projectId
RETURNING next_work_item_number - 1;
```

The implementation:

- reuses the connection owned by `WorkbenchDbContext`;
- participates in the current EF Core transaction when one exists;
- only closes the connection when it opened the connection itself;
- returns `null` when the Project does not exist;
- avoids `MAX(number) + 1`;
- avoids loading and mutating the Project entity for counter allocation.

Added PostgreSQL integration tests covering:

- sequential allocation;
- unknown Project handling;
- concurrent allocation using independent `DbContext` instances and database connections.

The concurrency test verified that multiple callers receive unique Project-scoped numbers.

## Engineering Decisions

### Dedicated Work Item number allocator

Decision:

> Work Item number allocation is represented by `IWorkItemNumberAllocator` rather than being added to `IProjectRepository`.

Reasoning:

- single responsibility;
- easier targeted testing;
- isolates concurrency-sensitive persistence behavior;
- prepares the capability to participate in the same transaction as Work Item creation.

### Database-controlled allocation

PostgreSQL is responsible for synchronizing concurrent updates to `projects.next_work_item_number`.

This prevents application-level race conditions and keeps number allocation atomic.
