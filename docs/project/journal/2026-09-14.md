## Architecture Notes

### Read and Write Responsibilities

The Work Item implementation now has two intentionally different abstractions.

`IWorkItemRepository` handles persistence/write responsibilities.

`IWorkItemQueries` handles optimized read operations and can project data across aggregate boundaries when required by API representations.

This avoids modifying the Work Item domain model solely to satisfy read-side presentation requirements.

### Project-Scoped Work Item Identity

A Work Item has:

- a UUIDv7 technical identifier
- a Project-scoped sequential number
- a derived human-readable code

Example:

`VEL-3`

The human-readable code is not persisted independently. It is derived from:

`Project.Key + WorkItem.Number`

### API Testing Strategy

VEL Workbench now uses two complementary API tools:

- Scalar for interactive API discovery and development.
- Bruno for repeatable, version-controlled API regression tests.

Manual `curl` validation remains useful during development but is not the primary regression evidence.
